# LETTY — Go-Live Runbook

This document lists everything that must be done **by hand** (dashboards, secrets,
deployment settings) before switching the site to real traffic. Code-side
hardening is already in place; these are the steps code cannot do for you.

---

## 1. Database status (verified 2026-09-21)

The Supabase Postgres project (`hjqylutputroxwmicdaq`, eu-central-1) is **live
and in use**: 2 products, 15 variants (all in stock), **18 orders**, 13
customers, 24 addresses. Missing entirely: **admins (0), reviews, coupons,
shipping methods**; `base_price_gbp` is NULL on products (GBP prices fall back
to a USD conversion — seed real GBP prices when convenient).

Two data gaps block launch and are fixed by steps below:
- **No admin account exists** → nobody can run the admin console. Fix in §3.
- **No reviews** → product pages correctly show "No reviews yet" until real
  customers review. Do NOT fabricate reviews (legal + SEO exposure).

> ⚠️ The `DATABASE_URL` in `backend/.env` contains a raw, unencoded password
> with `@` characters in it. Supabase-js (which the backend uses) works, but
> any `pg`-based script (e.g. `scripts/run-all-migrations.ts`) cannot parse
> that URL. When you next touch the DB password, URL-encode it
> (`@` → `%40`, and note it currently contains `.`/`1` chars which are fine).

## 2. Stripe — switch to LIVE keys

Everything is currently in **test mode**. Real money requires live keys:

1. Stripe Dashboard → Developers → API keys: copy the **live** keys.
   - `STRIPE_SECRET_KEY` (or a live *restricted* key scoped to what the backend
     needs) → Render env var on **letty-backend**.
   - `STRIPE_PUBLISHABLE_KEY` (pk_live_…) → Vercel env var on the frontend,
     **and** the backend (`STRIPE_PUBLISHABLE_KEY`) so they match.
2. Remove the test publishable key wherever it is set.
3. Stripe Dashboard → Developers → Webhooks → **Add endpoint**:
   - URL: `https://lettyecommerce.onrender.com/api/checkout/webhook/stripe`
   - Events: `payment_intent.succeeded`, `payment_intent.payment_failed`
   - Copy the signing secret → `STRIPE_WEBHOOK_SECRET` on Render.
4. In Stripe → Settings → Payment methods, enable the methods you want on the
   Payment Element (cards, Apple Pay, Google Pay, Link, etc.). Express
   Checkout wallets need a domain registered under
   Settings → Payment method domains (houseofletty.com + www).
5. Create the real products/prices or keep the DB-driven pricing (the backend
   prices from `product_variants` — no Stripe Price objects needed).

> The order pipeline cross-checks `livemode` on payment intents against the
> server key, so test/live mismatches fail loudly instead of recording
> phantom payments.

## 3. Create the first admin

The admin console requires a signed-in owner for every mutation, and the
database has **zero** admin rows. From `backend/`:

```bash
npm run db:create-admin -- you@houseofletty.com "YourStrongPassword" "Your Name"
```

Then sign in at `https://www.houseofletty.com/admin/login` (same-origin proxy
to the backend — cookies just work).

## 4. Rate limiting — no setup needed

Rate limiting and caching now run **in-process** (sliding-window limiter +
TTL map in `backend/lib/cache/redis.ts`). No Upstash account, no env vars.
Limits: checkout 10/min per IP, credential endpoints 5/min, public APIs
60/min. If you ever run more than one backend instance, move that module
onto a shared store — every call site already goes through the facade.

## 5. Background jobs — one shared secret

Job endpoints (`/api/jobs/*`) authorize either an admin session cookie or
the `x-jobs-secret` header equal to `JOBS_SECRET_KEY` (auto-generated by
render.yaml; visible in the Render dashboard).

Schedule them with any cron that can send a header — Render Cron Jobs, a
free cron service, or a GitHub Actions scheduled workflow:

```yaml
# .github/workflows/cron.yml (example)
on:
  schedule: [{cron: "0 6 * * *"}]
jobs:
  jobs-run:
    runs-on: ubuntu-latest
    steps:
      - run: |
          curl -fsS -X POST -H "x-jobs-secret: ${{ secrets.JOBS_SECRET_KEY }}" \
            https://lettyecommerce.onrender.com/api/jobs/abandoned-cart
          curl -fsS -X POST -H "x-jobs-secret: ${{ secrets.JOBS_SECRET_KEY }}" \
            https://lettyecommerce.onrender.com/api/jobs/review-requests
```

Suggested cadence: `abandoned-cart` and `review-requests` daily,
`inventory-sync` hourly, `algolia-reindex` weekly or on demand.
(`/api/jobs/post-payment` is invoked by the backend itself after payment —
no cron needed.)

## 7. Rotate exposed secrets

These values existed in plaintext in local env files and should be rotated
before launch:

- Resend API key (`re_…`) — rotate in Resend → API Keys, update Render.
- Cloudinary API secret — rotate in Cloudinary → Settings → Access Keys.
  (`render.yaml` previously contained the API key; it has been removed from
  the repo, but the key pair should still be rotated.)
- Database password — rotate in Supabase → Settings → Database, then update
  `DATABASE_URL` on Render (URL-encode special characters).
- `JWT_SECRET_KEY` — fine to keep if never shared; otherwise regenerate
  (regenerating signs out all customers/admins).

## 9. CORS / frontend origins

`FRONTEND_ORIGINS` on Render must contain exactly:
`https://www.houseofletty.com,https://houseofletty.com` (the localhost and
vercel.app entries in the current value are harmless but can be dropped).

## 10. Customer auth cookies (already code-side)

Customer login now posts **same-origin** (`/api/customer/auth/login` → proxied
to the backend), so the `customer_token` cookie is set on
`houseofletty.com` with `SameSite=None; Secure` in production. The backend
already sets those cookie flags. No action needed — this note exists to
explain why Safari/Chrome will no longer drop the session cookie.

## 11. Post-launch smoke test (5 minutes)

1. Buy the cheapest product with a real card (then refund in Stripe).
2. Confirm: order appears in `/admin/orders`, confirmation email arrives,
   inventory decremented (check `/api/public/inventory` or the DB).
3. Try Apple Pay / Google Pay on a phone.
4. Check `/account/orders/<id>` while signed in (works) and signed out
   (must show the sign-in gate, never order data).
5. Verify webhook delivery in Stripe → Webhooks (200 responses).

## What was already fixed in code (summary)

- Frontend checkout deleted its own pricing/`paid` endpoints — all money flows
  through the backend orchestrator (server-priced, webhook-verified,
  idempotent). Client-supplied totals are ignored.
- Checkout now mounts Stripe **Express Checkout Element** (Apple Pay / Google
  Pay / Link) + **Payment Element** from the backend-issued `clientSecret`.
- `/account/orders/[id]` requires a signed-in customer session.
- Wishlist writes require a customer session (was: anyone, by email).
- Customer JWT no longer falls back to a hardcoded secret in production
  (auth fails closed instead).
- Job endpoints require a valid QStash signature in production (no open
  trigger).
- Rate limiting + caching moved in-process (Upstash/QStash dependencies
  removed entirely); the limiter is real now — it had been stubbed to
  always-allow. Also fixed a latent crash: middleware called the limiter
  without importing it (admin-login and checkout paths would have 500'd).
  Jobs authorize via `JOBS_SECRET_KEY` header or an admin session.
- Internal error messages are no longer leaked in production responses.
- Frontend no longer holds a direct Postgres connection (stock overlay and
  reviews now come from backend public APIs).
- First-admin bootstrap script added (`npm run db:create-admin`).
- Fabricated reviews and invented aggregate ratings removed; JSON-LD now
  includes `aggregateRating` only from real reviews, priced as GBP.
- `.env.example` files added for both apps; committed Cloudinary API key
  removed from `render.yaml`.
